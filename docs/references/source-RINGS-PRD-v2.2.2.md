## 0. 文档范围与版本说明

### 0.1 本版依据

本版以此前整理的旧项目 TDO PRD v2.1、V2.0
全量交互原型的业务流程，以及本轮用户确认的领域概念为基础。

本版明确采纳的用户决策：

1.  所有尚未正式分流的内容统一进入候选事项池。
2.  候选事项统一列表管理，通过固定分类和自定义标签筛选。
3.  候选事项定期回顾，不要求每天清空，也不以清空 Inbox 作为绩效。
4.  候选事项包含十种分类标签：备忘（Memo）、资料（Resource）、想法（Idea）、愿望（Wish）、待办种子（Task Candidate）、问题（Issue）、待决策（Decision）、承诺（Commitment）、事件（Event）、等待（Waiting）。
5.  候选事项通常由名称和备注说明构成；备注应支持列表式、多条记录。
6.  候选事项可以带有时间信息，但必须区分截止时间、事件时间、提醒时间、跟进时间和回顾时间。
7.  RINGS 的整体架构分为五层：捕捉层、规划层、执行层、可视调度层、管理层。
8.  执行层包含习惯管理。
9.  候选事项支持补充资料，包括图片、视频、音频、文档、其他文件，以及网页、文件和文件夹的外部引用。
10. 文件和文件夹可以使用路径或链接引用；默认不复制整个外部文件或文件夹。
11. 补充资料与候选事项分类是两个不同概念：例如“想法（Idea）”也可以关联图片、文档和文件夹。
12. 捕捉层、规划层和执行层是不同业务对象的管理区域，不是必须依次经过的流程步骤；它们共同构成事项和行动管理体系。
13. 可视化调度层是 RINGS 的默认首页和日常操作中心，主要从执行层获取已确认的任务进行时间安排。
14. 首页支持快速创建候选事项、正式任务、目标、习惯和日历事件，并提供未安排任务池。
15. 用户可以将没有具体执行时间的任务拖放到今天、某一天或某个时间段，创建或调整对应的 Plan。
16. 支持日、周、月、年不同时间尺度的计划视图；不同尺度采用适合的计划粒度，不要求年度计划精确到小时。

### 0.3 术语使用规则

-   **候选事项 Candidate：**
    捕捉层中的统一数据对象。不要再将其狭义理解为"候选任务"。
-   **候选事项分类 Category：**
    十种固定分类之一，用于说明候选事项是什么。
-   **自定义标签 Tag：** 用户自由添加的补充标记，与固定分类不同。
-   **执行任务 Task：** 用户已经确认承担并决定执行的行动对象。
-   **计划 Plan：** 对执行任务或习惯执行实例的时间安排。
-   **截止时间 Deadline：**
    一项行动必须完成的时间约束，不等于计划开始时间。

# 1. 产品定义

## 1.1 产品定位

RINGS（年轮）是一款面向个人知识工作、生活事务和长期成长的管理工具。

它帮助用户把日常出现的信息、资料、想法、愿望、问题、责任事项和事件统一捕捉，再根据实际意图分流到目标规划、任务执行、习惯养成和日历调度中。

RINGS 不只是 Todo 列表，也不只是番茄钟。它需要解决五类连续问题：

1.  **捕捉：** 临时出现的信息、想法、资料和事项，如何快速保存？
2.  **规划：**
    想往哪个方向发展？希望实现什么可衡量的目标？目标如何拆成阶段？
3.  **执行：** 已经承诺的事情如何拆分、执行、等待、完成和复盘？
4.  **调度：** 任务、习惯和事件如何放到时间维度中观察与安排？
5.  **管理：** 如何分类、关联、归档、恢复、统计和备份？

## 1.2 产品核心原则

1.  **先捕捉，后分类。** 快速输入时不要求用户先判断完整业务归属。
2.  **候选事项统一管理。** 备忘（Memo）、资料（Resource）、想法（Idea）
    等是候选事项的分类，不是十套独立的收集系统。
3.  **分类与状态分离。** 分类说明"它是什么"；状态说明"它现在怎么样"。
4.  **候选不等于任务。**
    只有用户明确承担行动责任或确认执行，才进入执行层。
5.  **时间字段语义必须明确。**
    截止时间、计划时间、事件时间、提醒时间不能混用。
6.  **目标与任务分离。** Goal 描述要达到的结果，Task 描述采取的行动。
7.  **习惯与普通任务分离。** Habit
    是重复规则，每一次执行是独立的发生记录。
8.  **计划与实际分离。** Plan 是安排，WorkSession 是实际执行记录。
9.  **允许长期保留。** 候选事项定期回顾即可，不要求每日清空。
10. **归档可恢复。** 归档不等于删除，不破坏来源和历史记录。
11. **不强制所有事情进入目标体系。**
    临时任务、生活琐事和突发工作可以独立执行。
12. **本地优先、平台适配。** Desktop 与 Web
    共用核心领域模型，系统能力按平台实现。

## 1.3 产品总体业务流

``` text
捕捉层 Capture
    │
    ├── 保留为备忘 / 资料
    ├── 继续孵化为想法 / 愿望
    ├── 澄清为待办种子 / 问题 / 决策 / 承诺
    ├── 转为日历事件
    └── 转为正式目标或执行任务
              │
              ▼
规划层 Planning
    Direction → Goal → Stage
              │
              ▼
执行层 Execution
    Task / Subtask / Habit / WorkSession
              │
              ▼
可视调度层 Visual Scheduling
    Plan / Calendar / Timeline / Gantt
              │
              ▼
管理层 Management
    分类 / 关联 / 回顾 / 统计 / 归档 / 备份
```

以上是业务流，不代表每个对象必须按单一顺序流转。临时任务可以直接进入执行层；习惯可以独立存在；事件也可以不关联任何目标。

# 2. 总体架构：五层业务体系

## 2.1 架构理解：五层不是线性流程

RINGS 的五层架构分别承担不同的管理职责，不要求用户必须从第一层依次走到第五层。

捕捉层、规划层和执行层管理的是不同成熟度、不同性质的事项与行动对象：

- 捕捉层：收集尚未整理或尚未决定如何处理的候选事项。
- 规划层：组织长期方向、目标和阶段，明确希望实现什么结果。
- 执行层：管理已经确认要做的任务、子任务和习惯。
- 可视化调度层：将执行层中需要执行的任务安排到具体时间，是首页和日常操作中心。
- 管理层：为所有业务对象提供分类、关联、回顾、统计、归档和备份能力。

可视化调度层不负责决定一个候选事项是否值得做，也不负责拆解目标；它主要负责回答：**已经确定要做的事情，什么时候做、安排多少时间、如何调整顺序。**

## 2.2 五层职责

### 2.2.1 捕捉层 Capture

**职责：** 统一收集尚未整理、尚未承诺或暂时不需要进入执行体系的内容。

核心对象：

- Candidate：候选事项统一实体。
- Category：十种固定分类。
- CandidateNote：多条备注记录。
- Material：补充资料和外部引用。
- Tag：自定义标签。

捕捉层回答：**这是什么？要不要处理？以后是否可能转化为行动？**

### 2.2.2 规划层 Planning

**职责：** 管理长期发展方向、可衡量目标和目标实现阶段。

核心对象：

- Direction：发展方向。
- Goal：目标。
- Stage：阶段。

核心关系：

```text
Direction 1 ── N Goal
Goal 1 ── N Stage
Goal 1 ── N Task（允许直接关联）
Stage 1 ── N Task
```

规划层回答：**希望实现什么？为什么做？需要经过哪些阶段？**

原则：

- Direction 是长期方向，可以没有期限。
- Goal 描述可衡量的结果，原则上设置目标期限。
- Stage 表示实现目标的阶段，不等同于任务。
- Stage 可以关联多个 Task。
- Task 可以不属于任何 Goal 或 Stage。
- 规划层可以创建任务，但任务创建后由执行层管理。

### 2.2.3 执行层 Execution

**职责：** 管理已经确认要做、需要推进或持续重复的行动。

核心对象：

- Task：正式执行任务。
- Subtask：子任务。
- Habit：习惯规则。
- HabitOccurrence：某一次习惯执行实例。
- WorkSession：实际工作会话。
- Thought：执行过程中的思考记录。
- WorkContext：任务相关的外部工作现场。

执行层回答：**有哪些事情已经确定要做？当前进展如何？下一步是什么？**

原则：

- Task 是明确的行动责任。
- Task 可以来自 Candidate、Goal、Stage，也可以是临时新增。
- Task 可以没有时间安排，保留在未安排任务池。
- Habit 是重复规则，不是一个永久存在的普通 Task。
- WorkSession 记录实际投入，不等于计划时长。

### 2.2.4 可视化调度层 Visual Scheduling

**职责：** 作为 RINGS 的默认首页，把执行层中的任务、习惯执行实例和日历事件放入时间视图，帮助用户安排和调整时间。

核心对象与视图：

- Plan：Task 或 HabitOccurrence 的执行安排。
- Calendar Event：日历事件。
- Unscheduled Tasks：尚未安排时间的执行任务池。
- Timeline：日 / 周 / 月时间线。
- Year Roadmap：年度目标、阶段和重要里程碑视图。

可视化调度层回答：**什么时候做？今天、这周、这个月和今年如何安排？**

原则：

- 调度对象主要来自执行层，不把所有 Candidate 直接放到时间线上。
- 用户可以从未安排任务池拖动 Task 到具体日期或时间段。
- 拖放操作创建或调整 Plan，不会重新创建 Task。
- Candidate 只有在用户确认转换为 Task 后，才能作为执行任务被安排。
- Calendar Event 作为时间事件显示在时间线上，但不自动变成 Task。
- Deadline、Plan Time、Event Time 必须区分。
- 首页同时提供快速创建入口，不要求用户离开首页才能创建事项。

### 2.2.5 管理层 Management

**职责：** 为其他四层提供统一管理能力。

包括：

- Collection：分类目录。
- Tag：自定义标签。
- Relation：跨对象关联。
- Lifecycle：完成、取消、归档、恢复和删除。
- Review：周期回顾。
- Statistics：统计分析。
- Backup / Export：备份和导出。
- Settings：偏好、通知、快捷键和平台设置。

管理层是跨层管理机制，不是必须独立存储所有数据的业务实体集合。

## 2.3 业务对象流转关系

```text
捕捉层 Capture
  Candidate（候选事项）
       │ 用户判断与确认
       ├──────────────→ 保留 / 归档 / 关联
       ├──────────────→ Direction / Goal（进入规划）
       ├──────────────→ Task（进入执行）
       └──────────────→ Calendar Event（进入日历）

规划层 Planning
  Direction → Goal → Stage
                    │ 创建或拆解行动
                    ▼
执行层 Execution
  Task / Subtask / Habit
       │ 已确认的行动任务
       ▼
可视化调度层 Visual Scheduling（默认首页）
  未安排任务池 → 拖放到日 / 周 / 月计划 → Plan
       │
       ▼
执行记录 WorkSession / HabitOccurrence
       │
       ▼
管理层 Management：回顾、统计、归档、关联
```

以上是常见业务关系，不是强制的单向工作流。临时任务可以直接创建在执行层；独立习惯可以不关联目标；事件也可以直接从首页创建。

## 2.4 首页与业务层的关系

首页是可视化调度工作台，不是新的业务数据层。

- 首页展示执行层中待安排和已安排的 Task。
- 首页展示当天应执行的 HabitOccurrence。
- 首页展示相关 Calendar Event。
- 首页提供 Candidate、Task、Goal、Habit、Event 等快速创建入口。
- 首页可以查看目标和阶段的摘要，但完整管理仍在规划层。
- 首页的拖放、改期和时间块调整，最终写入 Plan 数据。

# 3. 捕捉层：Candidate 候选事项体系

## 3.1 核心定义

Candidate
是所有尚未正式分流、尚未明确归属或暂时不需要进入执行体系的事项的统一数据对象。

它可能是信息、资料、想法、愿望、待办种子、问题、待决策事项、承诺、事件或等待事项。

Candidate 不意味着用户一定要执行它。

### 3.1.1 固定分类

本版采用十种固定分类。每条 Candidate
默认选择一个主要分类，同时允许添加多个自定义 Tag。

  -----------------------------------------------------------------------------------------------------------
  分类              英文标识          定义                                   示例
  ----------------- ----------------- -------------------------------------- --------------------------------
  备忘              备忘（Memo）              未来可能需要查阅的信息                 地址、尺寸、约定细节、电话号码

  资料              资料（Resource）          外部内容及其来源                       网站、文章、视频、GitHub
                                                                             项目、AI 对话、教程

  想法              想法（Idea）              尚未形成明确执行方案的创意或思路       开发一个新软件、设计 AI 工具

  愿望              愿望（Wish）              想做、想体验或想获得，但尚未承诺       旅行、学习摄影、购买设备

  待办种子          待办种子（Task Candidate）    已能描述具体行动，但尚未正式承诺执行   研究招聘网站、整理简历

  问题              问题（Issue）             发现的问题、故障、风险或障碍           电脑运行缓慢、项目 Bug

  待决策            待决策（Decision）          尚未确定选择，需要比较或权衡           是否换工作、选择技术方案

  承诺              承诺（Commitment）        自己答应别人或别人委托自己处理的事项   帮朋友修改简历、按时交付文件

  事件              事件（Event）             有明确发生时间或时间范围的事项         婚礼、预约、会议、考试

  等待              等待（Waiting）           等待外部回复、审核、交付或条件满足     等待面试通知、等待客户反馈
  -----------------------------------------------------------------------------------------------------------

### 3.1.2 分类边界

-   分类是固定的主要类型，不应无限增加。
-   自定义 Tag 用于补充主题、领域、来源、优先级等维度。
-   等待（Waiting） 在捕捉层是分类；进入执行层后，等待也可以成为 Task
    的生命周期状态或阻塞状态。
-   承诺（Commitment） 如果已经明确承担行动责任，不应长期停留在候选池，应转为
    Task。
-   事件（Event） 如果已经确认具体发生时间，应进入 Calendar 事件（Event）。
-   待办种子（Task Candidate） 如果已经决定执行，应转为正式 Task。
-   备忘（Memo） / 资料（Resource） 可以长期保留，不要求转成 Task。

## 3.2 Candidate 数据结构

Candidate 采用统一字段结构，不根据十种分类分别建立十张业务表。

  字段           类型             必填 说明
  -------------- -------------- ------ ----------------------------------
  id             ID                 是 唯一标识
  title          String             是 候选事项名称
  category       Enum               是 十种固定分类之一
  note_entries   List               否 多条备注说明
  tags           Relation\[\]       否 自定义标签
  source_uri     String             否 原始 URL 或外部地址
  source_type    Enum               否 手动、网页、AI 会话、文件等
  attachments    Relation\[\]       否 附件或外部资源引用
  time_info      Object             否 截止、事件、提醒、跟进或回顾时间
  review_at      DateTime           否 下次回顾时间
  status         Enum               是 候选事项生命周期状态
  created_at     DateTime           是 创建时间
  updated_at     DateTime           是 更新时间
  converted_to   Relation           否 转换后的对象
  archived_at    DateTime           否 归档时间

### 3.2.1 标题与备注

Candidate 的基础编辑体验应保持简单：

-   名称 / 标题：一句话描述事项。
-   备注：采用列表形式，支持多条信息。
-   备注支持新增、编辑、删除、排序。
-   每条备注可以记录创建时间。
-   资料（Resource） 类型可以在备注中记录摘要、阅读收获和关键内容。
-   备忘（Memo） 类型可以通过多条备注记录不同信息点。
-   不要求用户在捕获时填写完整描述。

建议的备注结构：

``` json
{
  "title": "研究某招聘网站",
  "category": "resource",
  "note_entries": [
    {
      "content": "网址：https://example.com",
      "created_at": "2026-11-17T10:00:00"
    },
    {
      "content": "主要提供技术岗位招聘信息",
      "created_at": "2026-11-17T10:05:00"
    },
    {
      "content": "后续可以研究岗位筛选功能",
      "created_at": "2026-11-17T10:10:00"
    }
  ]
}
```

以上仅为逻辑结构示例，不代表最终数据库字段格式已经冻结。

## 3.2.2 补充资料（Attachments & References）

### 3.2.2.1 定义

补充资料用于为 Candidate 提供图片、媒体、文档、文件和外部资源入口。它不是 Candidate 的分类，也不改变 Candidate 的主要类型。

例如：

- 一条“想法（Idea）”可以关联设计草图、参考图片和一个项目文件夹。
- 一条“资料（Resource）”可以关联原始网页、PDF、视频和摘要。
- 一条“问题（Issue）”可以关联报错截图、日志文件和复现视频。
- 一条“承诺（Commitment）”可以关联交付文档和相关文件夹。

补充资料应支持在 Candidate 转换为 Goal、Task、Event 或其他正式对象后继续保留关联，不因转换而丢失。

### 3.2.2.2 支持的资料类型

| 类型 | 英文标识 | 示例 | 建议处理方式 |
|---|---|---|---|
| 图片 | Image | PNG、JPG、WebP、GIF | 可添加附件；支持缩略图和预览 |
| 视频 | Video | MP4、MOV、WebM | 可添加附件；展示文件信息，支持时长和预览能力（视平台而定） |
| 音频 | Audio | MP3、WAV、M4A | 可添加附件；展示文件信息和播放入口（视平台而定） |
| 文档 | Document | PDF、DOCX、XLSX、PPTX、MD、TXT | 可添加附件；优先提供文件名、类型和预览入口 |
| 其他文件 | File | ZIP、工程文件、模型文件等 | 支持附件或外部引用 |
| 网页链接 | Web Link | 网站、GitHub、在线教程 | 保存 URL、标题和用户备注 |
| 文件引用 | File Reference | 本地文件、网络文件 | 保存路径或 URI，不默认复制 |
| 文件夹引用 | Folder Reference | 项目目录、素材目录、工作流目录 | 保存路径或 URI，不复制目录内容 |

### 3.2.2.3 两种核心管理方式

**A. 文件附件（Managed Attachment）**

用户通过文件选择器、拖拽或粘贴等方式添加文件，由 RINGS 将文件保存到自身管理的附件存储位置。

适用场景：
- 用户希望资料随 RINGS 数据一起备份。
- 文件体积和格式适合由应用管理。
- 用户希望在不同页面统一查看附件。

要求：
- 保存文件副本，不应未经确认移动或删除用户原文件。
- 保存原始文件名、文件类型、大小、添加时间和存储位置。
- 支持移除 RINGS 中的附件关联。
- 移除附件时明确区分“仅解除关联”和“删除 RINGS 管理的副本”。
- 大文件应提示大小，并允许用户取消。
- 图片可生成缩略图；媒体预览按平台能力逐步实现。

**B. 外部引用（External Reference）**

用户只提供 URL、文件路径或文件夹路径，RINGS 保存引用信息，不复制原始文件。

适用场景：
- 文件已经存放在用户自己的目录中。
- 大型素材库、模型目录、视频目录或工程目录。
- 网络共享目录或 NAS 路径。
- 在线网页、GitHub 仓库、云盘分享链接。

要求：
- 保存引用类型、显示名称、原始 URI / 路径和可选备注。
- 用户点击后尝试打开对应网页、文件或文件夹。
- 不默认扫描文件夹内容，不默认递归导入文件。
- 不自动移动、重命名或删除外部文件。
- 引用不可用时显示“无法访问 / 路径失效 / 权限不足”等状态。
- 用户可以手动重新定位或更新引用路径。

### 3.2.2.4 文件夹引用规则

文件夹引用是 RINGS 的重要能力，建议首版纳入需求。

示例：

```text
名称：ComfyUI 工作流资料
类型：文件夹引用（Folder Reference）
路径：F:\AI\ComfyUI\Workflows
备注：人物换装、角色一致性和图片编辑工作流
```

规则：

1. 保存文件夹路径或 URI，不复制文件夹。
2. 点击“打开文件夹”时，由 Desktop 客户端调用操作系统打开对应位置。
3. 文件夹内新增或修改文件时，RINGS 中的引用仍指向原目录。
4. 首版不默认递归扫描文件夹，也不自动建立文件索引。
5. 用户可以主动执行“检查路径”或“重新定位”。
6. 文件夹不存在或权限不足时，保留记录并标记不可用，不自动删除。
7. 支持用户为文件夹引用添加说明、标签和关联对象。
8. 可以将同一个文件夹引用关联到多个 Candidate、Goal 或 Task，避免重复登记。

### 3.2.2.5 Desktop 与 Web 的平台差异

**Desktop：**
- 支持通过文件选择器选择文件。
- 支持通过文件夹选择器选择目录（取决于桌面技术栈）。
- 支持保存本地绝对路径和系统可访问的网络路径。
- 支持点击路径打开文件或文件夹。
- 支持拖拽文件添加附件。
- 对外部引用提供可用性检查和重新定位。

**Web：**
- 支持网页 URL 和在线资源链接。
- 支持用户主动上传文件作为 RINGS 管理的附件。
- 浏览器不能任意访问用户电脑上的绝对路径。
- 本地路径可以作为文本引用保存，但不能承诺在所有浏览器和设备上都能直接打开。
- 如需跨设备使用，应使用可访问的网页链接、云端链接或由用户上传的附件。

**跨设备注意事项：**
- 本地绝对路径只在对应设备和路径环境中有效。
- 后续如支持多设备同步，需要设计路径映射、共享目录或外部存储策略。
- 不应把一台设备的本地路径误认为所有设备都可访问。

### 3.2.2.6 引用状态

外部引用建议有以下状态：

| 状态 | 含义 |
|---|---|
| unchecked | 尚未检查 |
| available | 当前可访问 |
| unavailable | 路径或资源不存在 |
| permission_denied | 当前用户无访问权限 |
| unsupported | 当前平台不支持直接打开 |
| needs_relink | 用户需要重新定位资源 |

引用状态仅用于提示，不得因检查失败自动删除记录。

### 3.2.2.7 补充资料与其他概念的边界

- **资料（Resource）** 是 Candidate 的一种分类，表示这条候选事项本身是一份外部资料或资源。
- **补充资料（Attachments & References）** 是任意 Candidate、Goal、Task 等对象可以关联的文件或链接。
- 一条“想法（Idea）”可以附带多张图片，但它本身仍然是“想法（Idea）”。
- 一条“资料（Resource）”可以同时附带 PDF、视频和文件夹引用。
- **工作上下文（WorkContext）** 更侧重执行时需要打开的工作现场，例如代码仓库、终端、AI 会话或项目目录；补充资料更侧重说明、参考和证据。两者可以引用同一个外部位置，但用途不同。

### 3.2.2.8 补充资料的数据结构建议

建议在 Candidate 之外建立统一的 Attachment / ExternalReference 逻辑实体，并通过关联表挂载到不同业务对象。

| 字段 | 说明 |
|---|---|
| id | 唯一标识 |
| owner_type | 所属对象类型，如 Candidate、Goal、Task |
| owner_id | 所属对象 ID |
| material_type | image / video / audio / document / file / web_link / file_reference / folder_reference |
| storage_mode | managed_attachment / external_reference |
| display_name | 用户看到的名称 |
| uri | 网页 URL、文件 URI 或文件夹 URI |
| local_path | 本地路径（仅适用时） |
| mime_type | MIME 类型（可选） |
| file_size | 文件大小（可选） |
| preview_uri | 缩略图或预览资源位置（可选） |
| availability_status | 引用可用状态 |
| note | 补充说明 |
| created_at | 添加时间 |
| updated_at | 更新时间 |

以上为逻辑字段建议。正式数据库实现时，可根据 Desktop / Web 存储方式拆分附件元数据、文件实体和对象关联表。

### 3.2.2.9 操作与交互需求

Candidate 详情页的“补充资料”区域应支持：

- 添加文件。
- 添加网页链接。
- 添加文件路径。
- 添加文件夹路径。
- 拖拽添加文件（平台支持时）。
- 查看图片缩略图。
- 查看文件名、类型和大小。
- 打开文件 / 文件夹 / 网页。
- 编辑显示名称和备注。
- 重新定位失效路径。
- 解除关联。
- 管理 RINGS 内部附件副本。

添加补充资料时，应让用户明确知道当前操作是“上传副本”还是“仅保存引用”。

### 3.2.2.10 安全与数据保护

- 未经用户明确选择，不读取整个文件夹内容。
- 不自动递归扫描用户目录。
- 不自动上传外部引用指向的文件。
- 不自动移动、重命名或删除用户原始文件。
- 外部路径可能包含个人目录信息，界面展示和日志应避免不必要泄露。
- 打开文件或文件夹前，应遵循操作系统权限和应用授权。
- 对未知或高风险文件类型，不自动执行文件。
- 文件引用失效时保留元数据，允许用户重新定位。


## 3.3 时间信息：候选事项不等于没有时间

Candidate 可以包含时间信息，但时间字段必须标明语义。

  -----------------------------------------------------------------------------------------
  时间类型          字段建议          含义                       默认处理
  ----------------- ----------------- -------------------------- --------------------------
  截止时间          deadline_hint     可能需要在某日期前完成     判断是否已经形成执行责任

  事件时间          event_start /     事情实际发生的时间         转入 Calendar 事件（Event）
                    event_end                                    

  提醒时间          reminder_at       提醒自己查看或处理         保留 Candidate 提醒

  跟进时间          follow_up_at      何时检查等待事项           生成跟进提醒或 Task

  回顾时间          review_at         何时重新评估这条候选事项   保留在候选池并到期提示
  -----------------------------------------------------------------------------------------

不能把所有时间都叫 Deadline，也不能把"有日期"直接等同于"已计划"。

## 3.4 截止时间与执行事项的判断规则

这是本版的重要业务规则。

**判断一件事是否进入执行层，核心依据是是否存在明确的行动责任，而不是单纯有没有日期。**

  -----------------------------------------------------------------------------------------------
  场景                         应归属                  原因
  ---------------------------- ----------------------- ------------------------------------------
  下周五前必须把简历交给朋友   Task                    已承担明确行动责任和截止期限

  下周五下午参加面试           Calendar 事件（Event）          这是发生在特定时间的事件

  下周五提醒自己查看招聘网站   Candidate + Reminder    只是提醒，不一定需要执行任务

  下周五安排两小时修改简历     Task + Plan             有明确行动和计划时段

  下周五前决定是否购买电脑     可转 Task               若已承担决策责任，可创建"比较并决定"任务

  等待面试通知，下周一跟进     等待（Waiting） Candidate 或    取决于是否已经承担主动跟进责任
                               等待（Waiting） Task            
  -----------------------------------------------------------------------------------------------

### 3.4.1 自动判断建议

当用户给 Candidate 填写截止时间时，系统可以提示：

-   这是必须完成的行动期限吗？
-   这是一个实际发生的事件吗？
-   只是提醒自己以后查看吗？
-   是否需要在指定日期主动跟进？

系统可以根据用户选择建议转换，但不得未经确认自动改变对象类型。

## 3.5 Candidate 生命周期

建议状态：

  状态         含义
  ------------ --------------------------------------------
  new          刚刚捕获，尚未回顾
  reviewing    正在整理或判断
  retained     保留为备忘 / 资料 / 想法等，不需要立即处理
  incubating   继续孵化，等待未来评估
  converted    已转换为正式管理对象
  archived     暂时退出日常候选池，可恢复
  dismissed    已决定不再保留，可按回收站规则恢复或删除

说明：

-   不要求每天把 new 状态清空。
-   retained / incubating 可以长期存在。
-   review_at 到期后可提示回顾，不强制自动转换。
-   converted 候选项保留来源信息，不因转换而丢失。
-   archived 不等于 deleted。

## 3.6 候选事项分流

候选事项回顾时，允许以下操作：

1.  保留：继续留在候选池。
2.  转为 备忘（Memo） / 资料（Resource） 参考项：保留资料属性，进入对应筛选视图。
3.  转为 Direction：形成长期发展方向。
4.  转为 Goal：形成有衡量方式和期限的目标。
5.  转为 Task：形成明确行动责任。
6.  转为 Calendar 事件（Event）：形成时间事件。
7.  转为 Habit：形成重复执行规则。
8.  关联现有对象：不复制内容，建立关联。
9.  归档：暂时退出日常管理。
10. 取消 / 删除：明确不再保留。

备忘（Memo）、资料（Resource）、想法（Idea） 等分类不要求都转换为独立业务实体。v2.2 首版采用
Candidate
统一存储；只有形成正式目标、任务、习惯或事件时，才创建对应的正式对象。

## 3.7 候选池页面需求

-   统一列表视图。
-   支持十种分类筛选。
-   支持自定义标签筛选。
-   支持按创建时间、更新时间、回顾时间排序。
-   支持搜索标题和备注内容。
-   支持卡片视图与列表视图。
-   支持快速新增。
-   支持批量归档和批量修改标签。
-   支持单条事项查看备注列表和来源。
-   支持到期回顾提示。
-   支持"已保留""待回顾""已转换""已归档"等视图。
-   不显示强制清空进度，不以 Inbox 未清空作为失败指标。

# 4. 规划层 Planning

## 4.1 Direction：发展方向

定义：用户长期希望投入、提升或发展的领域。

示例：

-   职业发展
-   AI 技术能力
-   软件工程
-   英语能力
-   健康管理
-   个人创作

字段建议：

  字段                      说明  ------------------------- ----------------------------
  title                     方向名称
  description               方向说明
  tags                      领域标签
  status                    active / paused / archived
  review_cycle              可选回顾周期
  created_at / updated_at   时间记录

规则：

-   Direction 不强制设置截止日期。
-   一个 Direction 可以关联多个 Goal。
-   Direction 可以只有长期描述，不一定立刻创建 Goal。
-   Direction 可暂停或归档，不影响历史 Goal。

## 4.2 Goal：目标

定义：用户希望在一定时间内达到的、可描述和衡量的结果。

目标应尽量具备：

1.  目标名称。
2.  目标说明。
3.  衡量指标。
4.  当前基线值（如适用）。
5.  目标值与单位（如适用）。
6.  开始日期。
7.  目标期限。
8.  完成判定条件。
9.  所属 Direction（可选）。

目标示例：

-   在 2027-03-31 前获得一份符合条件的 Offer。
-   六个月内达到英语 B2。
-   在三个月内完成一个可上线的软件项目。

Goal 字段建议：

  字段                  说明
  --------------------- -----------------------------------------------------------
  title                 目标名称
  direction_id          所属方向，可选
  description           目标说明
  metric_type           数量、里程碑、布尔完成或自定义指标
  baseline_value        当前基线
  target_value          目标值
  unit                  单位
  start_date            开始日期
  due_date              目标期限
  completion_criteria   完成条件
  status                draft / active / paused / achieved / cancelled / archived
  progress_value        当前进度值或计算结果

### 4.2.1 目标进度规则

-   目标进度不能简单等于子任务完成率。
-   如果 Goal 有明确量化指标，应优先依据指标计算进度。
-   如果 Goal 由多个里程碑构成，可依据 Stage 完成情况辅助展示。
-   用户可以手动更新目标进度。
-   目标完成必须依据完成条件，而不是仅依据任务数量。

## 4.3 Stage：阶段

定义：实现一个 Goal 过程中划分的阶段性工作过程。

示例：

Goal：找到一份合适的新工作。

-   Stage 1：职业定位。
-   Stage 2：求职准备。
-   Stage 3：投递与面试。
-   Stage 4：Offer 评估与入职。

Stage 字段建议：

  字段                    说明
  ----------------------- ---------------------------------------------------
  goal_id                 所属 Goal
  title                   阶段名称
  description             阶段说明
  sort_order              阶段顺序
  start_date / due_date   计划时间范围，可选
  exit_criteria           阶段完成条件
  status                  pending / active / completed / paused / cancelled
  progress                阶段辅助进度

规则：

-   一个 Goal 可以有多个 Stage。
-   Stage 可以有多个 Task。
-   Stage 可以不设置固定时间。
-   Stage 必须有可判断的完成条件或交付结果。
-   Stage 完成不等于 Goal 完成。
-   Task 可以直接关联 Goal，不强制必须归属 Stage。
-   阶段顺序可以调整，但历史执行记录不能被覆盖。

## 4.4 Goal / Stage / Task 的关系

``` text
Direction
  ├── Goal A
  │    ├── Stage A1
  │    │    ├── Task 1
  │    │    ├── Task 2
  │    │    └── Task 3
  │    ├── Stage A2
  │    │    ├── Task 4
  │    │    └── Task 5
  │    └── Direct Task（不属于某个 Stage）
  └── Goal B
       └── Stage B1
```

# 5. 执行层 Execution

## 5.1 Task：正式执行任务

定义：用户已经确认承担并决定执行的具体行动。

Task 与 Candidate 的边界：

-   Candidate：尚未决定是否执行，或尚未整理清楚。
-   Task：已经确认要做。
-   Task 可以没有计划时间，但应具有明确行动内容。
-   Task 可以有 Deadline，但 Deadline 不代表已经安排了执行时段。

Task 来源：

-   Candidate 转换。
-   Goal / Stage 拆解。
-   临时新增（AdHoc）。
-   外部承诺或工作安排。
-   习惯某次执行需要的具体补充行动。

### 5.1.1 Task 字段建议

  字段                      说明
  ------------------------- --------------------------------------------------------
  title                     任务名称
  description               任务说明
  parent_task_id            父任务 ID，支持子任务
  goal_id                   关联目标，可选
  stage_id                  关联阶段，可选
  origin                    candidate / goal / stage / ad_hoc / commitment / other
  priority                  优先级
  deadline                  必须完成的期限
  estimate_minutes          预计时长
  execution_mode            倒计时 / 正计时 / 量词 / 不计时
  lifecycle_status          生命周期状态
  schedule_status           是否已安排
  next_action               下一步行动
  progress_config           数量或其他进度配置
  created_at / updated_at   时间记录

### 5.1.2 Task 与 Subtask

-   Task 与 Subtask 使用同一种 Task 数据结构。
-   通过 parent_task_id 建立父子关系。
-   支持多级拆分，但建议限制默认展示深度，避免无限嵌套。
-   父任务进度可根据子任务、量化指标或人工判断计算。
-   父任务完成规则必须明确：是否要求所有子任务完成，由用户或任务配置决定。
-   子任务可以单独安排 Plan 和执行 WorkSession。

### 5.1.3 临时任务与特殊任务

临时任务不需要创建独立实体。

例如：

-   突发电脑故障。
-   临时修改文件。
-   购买生活用品。
-   临时处理工作请求。

这些都可以直接创建 Task，并设置：

-   origin = ad_hoc
-   可选 priority
-   可选 deadline
-   可选 Plan
-   可选标签

临时任务不强制归属 Direction / Goal / Stage。

### 5.1.4 Task 状态

建议分开管理生命周期和调度状态。

生命周期：

  状态          说明
  ------------- --------------------
  ready         已确认，等待执行
  in_progress   正在执行
  waiting       等待外部回复或条件
  blocked       被问题或依赖阻塞
  completed     已完成
  cancelled     已取消
  archived      已归档

调度状态：

  状态          说明
  ------------- -----------------------
  unscheduled   尚未安排执行时间
  planned       已创建一个或多个 Plan

规则：

-   ready + unscheduled 是正常状态，不代表遗漏。
-   waiting 任务可以设置 follow_up_at。
-   blocked 任务可以关联阻塞原因或 问题（Issue）。
-   完成、取消和归档是不同含义。
-   任务完成后可以重新打开，但应保留完成历史。

## 5.2 Habit：习惯

定义：按照重复规则持续执行的行为。

Habit 是独立实体，不属于 Task Kind。

习惯不要求一定有 Goal 或 Stage。

三种关联方式：

1.  独立习惯：例如每天喝水。
2.  方向关联：例如每天学习英语，关联英语能力 Direction。
3.  目标关联：例如每天刷题，关联考试 Goal 和对应 Stage。

### 5.2.1 Habit 字段建议

  字段              说明
  ----------------- ----------------------------------------
  title             习惯名称
  description       习惯说明
  recurrence_rule   重复规则
  start_date        开始日期
  end_date          可选结束日期
  preferred_time    可选固定时间
  target_type       时长、数量、完成打卡等
  target_value      目标值
  unit              单位
  direction_id      可选方向
  goal_id           可选目标
  stage_id          可选阶段
  status            active / paused / completed / archived

### 5.2.2 重复规则

首版建议支持：

-   每天。
-   每周指定星期。
-   每月指定日期。
-   每隔 N 天。
-   每周达到指定次数。
-   可选指定执行时间或时间范围。

### 5.2.3 HabitOccurrence：习惯执行实例

Habit 是重复规则；HabitOccurrence 是每一次具体执行。

每次发生记录建议包含：

-   habit_id
-   occurrence_date
-   expected_time
-   actual_start_at
-   actual_end_at
-   actual_value
-   unit
-   status（pending / completed / skipped / missed / excused）
-   note

规则：

-   不得用一个永久 Task 表示每天重复的习惯。
-   每次完成都应形成独立历史记录。
-   暂停 Habit 不删除历史 Occurrence。
-   修改未来重复规则，不得重写历史记录。
-   习惯可以设置目标，也可以独立存在。
-   习惯是否需要关联 Goal / Stage 由用户决定。

## 5.3 WorkSession：实际工作会话

定义：用户实际投入工作的一个时间段。

支持：

-   开始。
-   暂停。
-   继续。
-   结束。
-   记录实际时长。
-   保存本次结果。
-   记录下一步。
-   记录 待决策（Decision） / Question / Thought。

WorkSession 默认关联 Task；HabitOccurrence 可按需记录实际执行时间。

正式实现应以时间戳和暂停累计时长计算，不应仅依赖页面每秒累加计时。

同一用户首版默认只允许一个活动 WorkSession。无 Task
的自由专注是否支持，列入待确认事项。

## 5.4 Thought：执行思考记录

用于记录执行过程中的：

-   Note
-   Question
-   待决策（Decision）
-   Conclusion
-   WorkSession Summary
-   Next Action

Thought 应保留来源和发生时间，可关联 Task、WorkSession、Candidate 或
Review。

## 5.5 WorkContext：工作上下文

保存继续任务时需要返回的外部环境：

-   AI 会话。
-   GitHub Repo。
-   文件夹。
-   文件。
-   网页。
-   终端。
-   自定义 URL / 路径。

WorkContext 保存引用和备注，不擅自复制、读取或删除外部资源。

打开 Context 不自动开始 WorkSession。

# 6. 可视化调度层 Visual Scheduling

## 6.1 产品定位：默认首页与日常操作中心

可视化调度层是 RINGS 的默认首页。用户打开软件后，首先看到当前时间范围内的计划、待安排任务、习惯执行和日历事件。

首页不是单纯的统计仪表盘，而是可以直接创建、拖动、安排、调整和启动执行的工作台。

核心目标：

1. 快速查看今天需要做什么。
2. 将执行层中尚未安排时间的任务快速拖入时间线。
3. 对已安排任务进行改期、延长、缩短和重新排序。
4. 提前规划本周、本月和本年度的任务及阶段。
5. 从首页快速创建 Candidate、Task、Goal、Habit 和 Calendar Event。
6. 从时间安排直接开始 WorkSession，记录实际执行。

## 6.2 首页主要区域

建议采用可调整的工作台布局。

### 6.2.1 顶部导航与时间范围切换

提供：

- 今日（Day）
- 本周（Week）
- 本月（Month）
- 年度（Year）
- 日期跳转
- 返回今天
- 快速创建
- 搜索
- 通知与设置

切换时间范围时，不改变底层业务对象，只改变计划的观察粒度。

### 6.2.2 快速创建区 Quick Create

首页提供统一创建入口，支持：

| 创建类型 | 创建结果 | 默认行为 |
|---|---|---|
| 捕捉事项 | Candidate | 快速输入，进入候选事项池 |
| 执行任务 | Task | 直接创建正式任务，默认进入未安排任务池 |
| 目标 | Goal | 创建目标，可选择 Direction |
| 习惯 | Habit | 创建重复规则 |
| 日历事件 | Calendar Event | 创建带发生时间的事件 |
| 发展方向 | Direction | 创建长期方向 |
| 资料引用 | Material / Reference | 添加网页、文件或文件夹引用 |

快速创建应支持最少字段创建，详细字段可以后续补充。

快速创建 Task 时，用户可以选择：
- 仅创建任务，不安排时间。
- 创建任务并立即安排到当前时间范围。
- 从已有 Goal / Stage 创建关联任务。

快速捕捉仍默认创建 Candidate，不应因为首页有调度能力就把所有输入都变成 Task。

### 6.2.3 时间线 Timeline

日视图以时间轴为主：

- 按时间顺序展示 Plan。
- 展示 Calendar Event。
- 展示 HabitOccurrence。
- 显示当前时间指示线。
- 支持拖放、调整时长和移动任务。
- 支持点击任务查看详情。
- 支持从时间块直接开始 / 继续 WorkSession。
- 显示 Deadline，但不得把 Deadline 误显示为实际执行时段。

日视图应支持：
- 小时刻度。
- 可配置工作时间范围。
- 全天事项区域。
- 无具体时间的当日事项区域。
- 任务冲突和时间重叠提示。
- 空闲时间的可视化。

### 6.2.4 未安排任务池 Unscheduled Tasks

首页应提供可折叠或可调整宽度的未安排任务池。

内容来自执行层：
- ready 且没有未来有效 Plan 的 Task。
- 已经改期但尚未重新安排的 Task。
- 用户主动标记为待安排的 Task。

列表支持：
- 搜索和筛选。
- 按优先级、Deadline、创建时间排序。
- 显示预计时长。
- 显示所属 Goal / Stage。
- 显示是否被阻塞或等待。
- 拖动到时间线。
- 快速创建 Task。

不应把 Memo、Resource 等 Candidate 直接混入未安排任务池。Candidate 需要先经过用户确认，转成 Task 后才能进入该池。

## 6.3 拖放调度：Task → Plan

这是首页的核心交互。

典型流程：

```text
执行层中已有一个 Task
       │
       ▼
显示在“未安排任务池”
       │ 用户拖动
       ▼
拖到今天的时间线上
       │
       ├── 拖到具体时间段
       │       ↓
       │   创建带 start_at / end_at 的 Plan
       │
       ├── 拖到当天日期或全天区域
       │       ↓
       │   创建当天 Plan（可暂不指定具体时刻）
       │
       └── 拖到其他日期
               ↓
           创建该日期的 Plan
```

交互规则：

1. 拖放已有 Task 不得创建重复 Task。
2. 拖放的结果是创建或更新 Plan。
3. 如果 Task 有 estimate_minutes，默认使用该时长生成时间块。
4. 如果没有预计时长，允许使用用户默认时长，或在拖放后让用户调整时间块长度。
5. 用户可以拖动时间块边缘调整时长。
6. 用户可以把任务拖到其他日期，完成改期。
7. 如果出现时间冲突，明确提示，不静默覆盖其他 Plan。
8. 拖放操作支持撤销。
9. 改期应保留必要的历史信息。
10. 用户可以将任务从时间线移回未安排任务池，取消未来 Plan，但不删除 Task。
11. 如果 Task 有 Deadline，拖放到 Deadline 之后时应提示风险。
12. 如果 Task 处于 blocked / waiting 状态，仍可安排跟进动作，但应明确显示其状态。

### 6.3.1 候选事项拖放规则

Candidate 不是执行任务，不应直接默认进入时间线。

如果用户尝试将可行动的 Candidate（例如“待办种子（Task Candidate）”或“承诺（Commitment）”）拖到时间线上，系统应先提示：

- 转换为正式 Task 并安排时间；
- 取消操作。

转换成功后保留来源 Candidate，再创建 Plan。

Memo、Resource 等纯信息类 Candidate 不提供直接拖入执行时间线的默认操作。

## 6.4 多时间尺度计划

RINGS 应支持日、周、月、年四种时间尺度。它们不是同一种时间线简单缩放，而是采用不同的计划粒度。

| 视图 | 主要用途 | 主要对象 | 典型粒度 |
|---|---|---|---|
| 日计划 Day | 安排今天具体执行什么 | Task Plan、HabitOccurrence、Calendar Event | 小时 / 时间块 |
| 周计划 Week | 分配一周任务和工作负载 | Task Plan、Deadline、Event、习惯 | 日期 / 半天 / 时间块 |
| 月计划 Month | 规划本月重点、任务和节点 | Task、Goal、Stage、Event、里程碑 | 日期 / 周 |
| 年度计划 Year | 规划年度方向、目标和阶段 | Direction、Goal、Stage、重要里程碑 | 年 / 季度 / 月 |

### 6.4.1 日计划

- 显示具体时间轴。
- 允许从未安排任务池拖入。
- 支持任务时间块调整。
- 显示习惯和日历事件。
- 支持开始专注和记录实际时间。

### 6.4.2 周计划

- 以一周七天为主要布局。
- 支持跨日拖动任务。
- 支持将任务先安排到某一天，不必指定具体小时。
- 展示每日任务量、预计时长和负载。
- 支持查看本周 Deadline 和 Calendar Event。
- 支持从周计划进一步细化为日计划。

### 6.4.3 月计划

- 以月历或周分组视图展示。
- 重点显示任务期限、事件、阶段节点和目标里程碑。
- 支持把任务安排到某一天。
- 支持查看每周负载和本月重点。
- 不要求所有任务都设置精确开始时间。

### 6.4.4 年度计划

- 以年度路线图（Year Roadmap）呈现。
- 重点展示 Direction、Goal、Stage 和关键里程碑。
- 支持按季度、月份组织目标与阶段。
- 可展示重要 Deadline 和年度事件。
- 不要求将全年任务提前安排到具体小时。
- 年度计划可以逐步细化为月计划、周计划和日计划。

### 6.4.5 多尺度计划的关系

```text
年度方向与目标
       ↓
年度阶段 / 关键里程碑
       ↓
月度重点与阶段任务
       ↓
每周任务分配
       ↓
每日时间块 Plan
       ↓
实际执行 WorkSession
```

这是从粗到细的规划方式，不要求用户一次性把全年安排全部确定。上层计划允许调整，下层日程根据实际情况持续更新。

## 6.5 Plan：执行安排数据

Plan 表示对某个 Task 或 HabitOccurrence 的时间安排。

Plan 与 Deadline 完全不同：

- Deadline：最晚必须完成的时间。
- Plan：打算什么时候执行。
- WorkSession：实际什么时候执行。

Plan 字段建议：

| 字段 | 说明 |
|---|---|
| owner_type | task / habit_occurrence |
| owner_id | 对应对象 ID |
| plan_date | 计划日期 |
| start_at | 计划开始时间，可选 |
| end_at | 计划结束时间，可选 |
| estimated_minutes | 计划时长 |
| precision | date_only / time_block |
| status | scheduled / rescheduled / cancelled / completed |
| previous_plan_id | 改期来源，可选 |

规则：

- Task 可以没有 Plan。
- Task 可以分配多个 Plan，例如分多次完成。
- Plan 可以只指定日期，不指定具体时间。
- Plan 可以被移动、拆分或取消。
- 改期保留历史记录。
- Plan 不代表实际完成。
- 任务实际投入以 WorkSession 为准。
- 对同一个 Task 的多个 Plan，应支持区分不同执行批次或拆分计划，避免重复计算任务完成度。

## 6.6 Calendar Event：日历事件

定义：发生在特定日期或时间段的事件。

示例：
- 会议、预约、婚礼、考试、旅行、面试。

Event 字段建议：
- title
- description
- start_at
- end_at
- all_day
- location
- participants（可选）
- source_candidate_id（可选）
- related_task_ids（可选）
- reminder_rule（可选）

规则：
- Event 不自动变成 Task。
- Event 可以关联准备任务或后续任务。
- Event 的发生时间不等于 Task Deadline。
- Event 显示在首页时间线上，但不进入未安排任务池。
- Event 结束不代表关联任务自动完成。

## 6.7 冲突、延期和调整

- 系统可以提示同一时间段的计划冲突。
- 用户可以选择保留冲突、调整时间或取消计划。
- 系统可以提示 Deadline 风险。
- 不自动静默移动用户的其他任务。
- 任务延期时可以建议重新安排，但由用户确认。
- 计划变更不得覆盖历史 WorkSession。
- 支持撤销最近一次拖放和调度操作。

## 6.8 首页启动执行

用户点击时间块中的 Task：
- 查看任务详情。
- 开始 WorkSession。
- 暂停 / 继续 / 结束。
- 记录本次结果和下一步。
- 完成 Task 或标记阻塞。
- 返回首页后更新实际执行状态。

计划时间与实际时间必须分开展示。

# 7. 管理层 Management

## 7.1 Collection：分类目录

Collection 用于按项目、领域或主题组织对象。

建议支持：

-   多级目录。
-   图标、颜色、排序。
-   Task、Candidate、Goal、Habit 等对象关联 Collection。
-   对象可以不属于 Collection。
-   Collection 归档不影响其内部对象的历史记录。
-   Collection 与 Direction 不同：前者用于组织，后者用于发展方向。

## 7.2 Tag：自定义标签

Tag 用于横向标记对象，例如：

-   工作
-   生活
-   AI
-   学习
-   紧急
-   等待回复
-   需要研究

固定 Category 与 Tag 分离：

-   Category：Candidate 十种固定分类之一。
-   Tag：用户自定义的补充标记。
-   Priority：优先级，不是 Tag。
-   Status：生命周期状态，不是 Tag。

## 7.3 Relation：对象关联

允许跨层对象建立关联，例如：

-   Candidate ↔ Goal。
-   Candidate ↔ Task。
-   资料（Resource） ↔ Task。
-   Direction ↔ Goal。
-   Goal ↔ Stage。
-   Stage ↔ Task。
-   Task ↔ Task。
-   Task ↔ WorkContext。
-   Task ↔ Thought。
-   事件（Event） ↔ Task。

关联应保存关系类型和来源，不通过复制内容替代关联。

## 7.4 归档、取消、完成与删除

归档不是独立业务实体，而是跨对象生命周期机制。

  操作        含义                         可恢复
  ----------- ---------------------------- --------------------
  Completed   已达到完成条件               可以重新打开
  Cancelled   决定不再继续                 可以重新激活
  Archived    暂时退出日常管理，保留历史   可以恢复
  Deleted     用户明确删除                 依据回收站策略恢复

规则：

-   删除 Task 不得误删 WorkSession、Thought 和来源 Candidate。
-   归档 Candidate 不得删除其备注和来源。
-   归档 Goal 不应自动删除 Stage / Task。
-   取消 Goal 时，应提示用户处理未完成的关联 Task。
-   归档操作应可追踪时间和原因。

## 7.5 Review：周期回顾

回顾对象：

-   Candidate Pool。
-   Direction / Goal / Stage。
-   未完成 Task。
-   等待（Waiting） / Blocked Task。
-   Habit 执行情况。
-   计划与实际偏差。

回顾原则：

-   Candidate 定期回顾，不要求每日清空。
-   到达 review_at 可以提醒用户。
-   用户可选择保留、转换、归档或删除。
-   不自动把建议变成 Task。
-   回顾产生的结论可以记录为 Thought 或 Candidate。

## 7.6 Statistics：统计

建议统计：

-   Task 完成数量。
-   实际投入时间。
-   Plan 与 Actual 对比。
-   Goal 指标进度。
-   Stage 完成情况。
-   Habit 完成率和连续执行情况。
-   Candidate 分类数量及转化情况。
-   等待（Waiting） / Blocked 数量和停留时间。

统计规则：

-   不同对象类型不得混合计数。
-   不同单位的量词不得合并。
-   目标进度优先采用 Goal 指标，不简单使用 Task 完成率。
-   统计仅用于观察，不自动修改业务对象状态。

## 7.7 Backup / Export

首版至少规划：

-   Candidate 数据导出。
-   Goal / Stage / Task / Habit 数据导出。
-   WorkSession 历史导出。
-   JSON 全量备份。
-   数据恢复和版本迁移策略。

CSV / Excel / PDF 可作为后续导出格式。

# 8. 信息架构与页面结构

## 8.1 默认首页：可视化调度工作台

RINGS 默认打开首页（Scheduling Home），而不是候选事项列表或统计仪表盘。

首页采用“时间视图 + 未安排任务池 + 快速创建”的工作台结构。

建议桌面端布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ RINGS       今日  本周  本月  年度       搜索   + 创建   设置 │
├──────────────────────────────────────────────────────────────┤
│ 快速创建：捕捉事项  任务  目标  习惯  日历事件  资料引用       │
├──────────────────────────────────────┬───────────────────────┤
│                                      │ 未安排任务             │
│         当前时间范围的可视时间线      │ ┌───────────────────┐ │
│                                      │ │ 优化简历编辑器     │ │
│  09:00 ── 任务 A                      │ │ 预计 90 分钟       │ │
│  10:00 ── 任务 B                      │ ├───────────────────┤ │
│  12:00 ── 午间 / 空闲                 │ │ 研究图片编辑模型   │ │
│  14:00 ── 任务 C                      │ │ 预计 60 分钟       │ │
│  16:00 ── 习惯 / 事件                 │ └───────────────────┘ │
│                                      │                       │
└──────────────────────────────────────┴───────────────────────┘
```

首页区域：

1. 顶部时间范围导航。
2. 快速创建区。
3. 主时间视图。
4. 未安排任务池。
5. 今日摘要与执行状态。
6. 可选目标 / 阶段摘要。

首页允许用户根据屏幕大小调整区域宽度和折叠侧栏。

## 8.2 页面与导航结构

| 页面 / 入口 | 所属业务层 | 主要职责 |
|---|---|---|
| 首页 Scheduling Home | 可视化调度层 | 默认首页；日 / 周 / 月 / 年计划；拖放调度 |
| Candidate Pool | 捕捉层 | 统一候选事项列表、分类和回顾 |
| Candidate Detail | 捕捉层 | 标题、备注、补充资料、来源和时间信息 |
| Planning | 规划层 | Direction、Goal、Stage 管理 |
| Goal Detail | 规划层 | 目标指标、阶段、关联任务 |
| Task Library | 执行层 | 正式任务、父子任务、状态和未安排任务 |
| Habit Center | 执行层 | 习惯规则、重复计划和历史记录 |
| Focus | 执行层 | WorkSession、Thought、Next Action |
| Calendar / Timeline | 可视化调度层 | 首页内的不同时间尺度视图；必要时可独立打开 |
| Review | 管理层 | 候选事项、目标、任务和习惯的周期回顾 |
| Statistics | 管理层 | 目标、任务、习惯和时间统计 |
| Collections / Tags | 管理层 | 分类目录和标签管理 |
| Settings | 管理层 | 数据、备份、通知、快捷键和平台设置 |

## 8.3 全局快速创建

首页和全局快捷键提供统一创建入口：

- 捕捉事项：默认创建 Candidate。
- 新建任务：直接创建 Task，默认进入未安排任务池。
- 新建目标：创建 Goal，可选择 Direction。
- 新建习惯：创建 Habit。
- 新建日历事件：创建 Calendar Event。
- 新建方向：创建 Direction。
- 添加资料引用：创建 Material / Reference 并选择关联对象。

创建入口应采用轻量表单，避免用户每次创建都填写完整字段。

## 8.4 导航原则

- 默认进入首页可视化调度工作台。
- 用户可以从任何页面快速捕获 Candidate。
- 用户明确要执行时，可以直接创建 Task，不必先经过 Candidate。
- Candidate 转 Task 后保留来源关系。
- Goal / Stage 页面可以创建关联 Task。
- Task 可以直接安排 Plan。
- 首页拖动 Task 只改变 Plan，不改变 Task 本身。
- Event 显示在时间线上，但不进入未安排任务池。
- Habit 根据重复规则生成执行实例，并在相应日期显示。
- Candidate 只有经过用户确认转换为 Task 后，才进入任务调度池。

# 9. 核心用户流程

## 9.1 快速捕获

``` text
用户触发 Quick Capture
    ↓
输入标题 / 内容
    ↓
默认创建 Candidate
    ↓
可选分类、标签和备注
    ↓
保存
    ↓
留在当前页面，不强制跳转
```

快速捕获最少只需要标题或内容。分类可以后补。

## 9.2 候选事项回顾

``` text
打开 Candidate Pool
    ↓
筛选 new / retained / incubating / 到期回顾
    ↓
查看标题、备注、来源和时间
    ↓
选择：
    ├── 保留
    ├── 继续孵化
    ├── 转为 Task
    ├── 转为 Goal / Direction
    ├── 转为 Event
    ├── 转为 Habit
    ├── 关联已有对象
    └── 归档 / 删除
```

## 9.3 Candidate → Task

``` text
选择 Candidate
    ↓
确认行动内容和责任归属
    ↓
补充 Deadline（可选）
    ↓
设置优先级、执行方式和 Next Action
    ↓
选择是否关联 Direction / Goal / Stage
    ↓
创建 Task
    ↓
保留来源 Candidate 和转换关系
    ↓
进入 Backlog 或直接创建 Plan
```

## 9.4 从未安排任务池拖放到今日时间线

```text
打开 RINGS 首页
    ↓
查看未安排任务池
    ↓
选择已有 Task
    ↓
拖动到今天的时间线上
    ↓
系统根据预计时长创建 Plan
    ↓
用户调整开始 / 结束时间
    ↓
保存计划
    ↓
时间线显示该任务
    ↓
到计划时间开始 WorkSession
```

如果 Task 没有预计时长，允许用户拖放后调整时间块，或使用默认时长。

## 9.5 从首页快速创建并安排任务

```text
点击首页“新建任务”
    ↓
输入任务名称
    ↓
选择：
    ├── 仅创建：进入未安排任务池
    └── 创建并安排：选择日期 / 时间段
             ↓
          创建 Task + Plan
```

## 9.6 周 / 月 / 年计划逐步细化

```text
年度计划
  Direction / Goal / Stage / 关键里程碑
        ↓
月计划
  本月重点、阶段节点、任务期限
        ↓
周计划
  将任务分配到具体日期
        ↓
日计划
  将任务安排到具体时间块
        ↓
实际执行
  WorkSession / HabitOccurrence
```

用户可以从任意时间尺度开始规划，不要求必须先创建年度计划。

## 9.7 Candidate → Goal

``` text
选择 Idea / Wish / 待办种子（Task Candidate）
    ↓
明确希望实现的结果
    ↓
定义衡量方式
    ↓
设置目标期限
    ↓
选择所属 Direction（可选）
    ↓
创建 Goal
    ↓
拆分 Stage
    ↓
在 Stage 下创建 Task
```

## 9.8 Candidate 事件（Event） → Calendar 事件（Event）

``` text
选择 Event Candidate
    ↓
确认开始时间 / 结束时间
    ↓
补充地点、参与人和提醒
    ↓
创建 Calendar Event    ↓
可选创建准备 Task / 后续 Task
```

## 9.9 等待（Waiting） → 跟进

``` text
捕获 Waiting Candidate
    ↓
记录正在等待谁 / 什么
    ↓
设置预计回复时间或 follow_up_at
    ↓
判断是否需要自己主动跟进
    ├── 不需要：保留 Waiting Candidate
    └── 需要：创建 Waiting Task
                 ↓
             到期提醒跟进
                 ↓
             收到回复 / 完成跟进 / 继续等待
```

## 9.10 Habit 创建与执行

``` text
创建 Habit
    ↓
设置重复规则
    ↓
设置可选目标 / 方向 / 阶段关联
    ↓
生成 HabitOccurrence
    ↓
执行 / 完成 / 跳过
    ↓
保存历史记录
    ↓
统计周期完成情况
```

# 10. 核心业务规则

## 10.1 Candidate 与 Task 边界

1.  Candidate 是尚未正式分流的事项。
2.  Task 是用户已经确认承担的行动。
3.  Candidate 可以长期保留，不要求转换。
4.  Task 不要求必须有 Goal。
5.  有 Deadline 不自动等于 Task。
6.  有明确行动责任且必须完成的事项，应进入 Task。
7.  事件时间应进入 Calendar 事件（Event），不应伪装成 Task Deadline。
8.  仅需提醒查看的事项可以继续留在 Candidate。

## 10.2 Goal 与 Task 边界

1.  Goal 表示结果，Task 表示行动。
2.  Goal 可以有多个 Stage。
3.  Stage 可以关联多个 Task。
4.  Task 可以直接关联 Goal，也可以不关联。
5.  Goal 进度不等于 Task 完成率。
6.  Stage 必须有完成条件或交付结果。

## 10.3 Habit 与 Task 边界

1.  Habit 是重复规则。
2.  HabitOccurrence 是一次执行实例。
3.  Habit 可以独立存在。
4.  Habit 可以关联 Direction / Goal / Stage。
5.  历史执行记录不能因修改重复规则而丢失。
6.  Habit 暂停不等于删除。

## 10.4 时间边界

1.  Deadline 是完成约束。
2.  Plan 是执行安排。
3.  事件（Event） Time 是事件发生时间。
4.  Reminder Time 是提醒时间。
5.  Review Time 是回顾时间。
6.  WorkSession 是实际执行时间。
7.  不允许使用单一 date 字段表达所有时间语义。

### 10.4.1 时间尺度与调度粒度

- 年度计划：方向、目标、阶段和关键里程碑。
- 月度计划：重点、阶段节点、任务日期和事件。
- 周计划：将任务分配到具体日期，可选时间段。
- 日计划：将任务安排到具体时间块。
- 不要求用户提前确定全年所有任务的小时级时间。
- 从一个时间尺度切换到另一个时间尺度，只改变观察和编辑粒度，不改变 Task 的业务身份。

## 10.5 历史与数据完整性

-   对象转换必须保留来源关系。
-   归档不物理删除历史。
-   删除操作不得级联误删执行记录。
-   Plan 改期保留历史。
-   Habit 规则变更不修改历史 Occurrence。
-   Goal / Stage 调整不覆盖已经发生的 WorkSession。

## 11.2 关系约束


## 11.3 关键实现建议

-   Candidate 分类使用固定枚举；用户自定义内容放入 Tag。
-   CandidateNote 使用独立记录，避免将所有备注压入一个长文本字段。
-   Task 父子关系使用 parent_task_id。
-   Task 生命周期和调度状态分开。
-   Goal 指标字段应支持数值、单位和自定义判定。
-   Habit 重复规则应采用可扩展结构。
-   CalendarEvent 与 Task 分离。
-   Relation 需要记录关系类型和创建时间。
-   删除和归档采用安全策略，保留必要历史。

# 12. 非功能性需求

## 12.1 平台与存储

-   Desktop / Web 共用领域模型和核心业务规则。
-   Desktop 本地数据库方案建议优先评估 SQLite。
-   Web 本地存储方案需单独确认。
-   云同步不是本版已确认基线。
-   数据导出和备份需要纳入首版技术方案。
-   时间统一存储策略，展示时按用户本地时区处理。

## 12.2 性能目标

  指标           目标值
  -------------- ---------------------
  冷启动         小于 2 秒（目标值）
  常规页面加载   小于 500 ms
  本地搜索       小于 200 ms
  月视图渲染     小于 300 ms
  计时恢复       以时间戳校准

以上为目标值，需在正式实现中验证。

## 12.3 安全与隐私

-   Candidate 可能包含个人信息和外部链接。
-   WorkContext 可能包含本地路径、Repo 地址和 AI 会话链接。
-   不得在未授权情况下读取或上传外部文件。
-   云同步或 AI 自动识别必须明确权限、数据范围和退出方式。
-   密码、密钥等高敏感凭据不应以普通备忘明文保存，建议使用专门的密码管理工具。

## 12.4 可用性

-   Quick Capture 尽量键盘可达。
-   快速捕获不要求填写大量字段。
-   Candidate 详情支持列表式备注。
-   转换对象时展示必要字段，不要求重复录入来源信息。
-   完成、取消、归档、删除等操作应有明确反馈。
-   允许用户保留大量候选事项，不制造清空压力。

## 附录 A：v2.1 → v2.2 领域模型迁移原则

  v2.1 概念           v2.2 处理
  ------------------- -------------------------------------
  Record              迁移为 Candidate，原始内容保留
  想法（Idea）                迁移为 Candidate，category = 想法（Idea）
  备忘（Memo）                纳入 Candidate，category = 备忘（Memo）
  资料（Resource）            纳入 Candidate，category = 资料（Resource）
  Task                保留为正式执行实体
  Task Kind = Goal    移除该用法，迁移为独立 Goal
  Task Kind = Habit   移除该用法，迁移为独立 Habit
  Plan                保留，明确只表示执行安排
  WorkSession         保留，关联 Task 或 HabitOccurrence
  WorkContext         保留
  Thought             保留
  Collection          保留并扩展适用对象
  Archive             统一生命周期机制

迁移要求：

1.  不直接删除旧 Record / 想法（Idea） 数据。
2.  转换后的 Candidate 保留旧对象 ID 或来源映射。
3.  原有 Task 不因新增 Goal / Stage 而强制归属目标。
4.  原有 Goal / Habit 类型任务需要迁移为对应独立实体。
5.  原有 Plan 不得被误认为 Deadline。
6.  历史 WorkSession 不得因任务模型调整而丢失。

## 附录 B：本版明确不做的设计

-   不为十种候选事项建立十套独立收集页面。
-   不要求每条 Candidate 都变成 Task。
-   不要求所有 Task 都归属 Goal。
-   不要求所有 Habit 都关联 Goal。
-   不把有日期的所有事项都当作 Task。
-   不把 Calendar 事件（Event） 当作 Task。
-   不把 Plan 当作实际执行。
-   不把 Archive 当作删除。
-   不用单一进度百分比代替 Goal 的真实衡量标准。
-   不以 Candidate Pool 清空率衡量用户效率。
