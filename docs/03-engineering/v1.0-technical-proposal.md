# RINGS v1.0 技术方案冻结提案

> 日期：2026-11-20  
> 状态：待产品确认（proposal / not frozen）  
> 适用范围：从 HTML 原型转入正式应用开发前的技术评审  
> 依据：当前 PRD、领域模型、业务规则、技术架构草案、Roadmap、v0.9 规划工作区规格与验收记录

## 1. 当前基线核验

截至本提案提交时，仓库包含产品文档与 HTML 原型，尚未包含正式应用源码。v0.9 规划工作区仍以浏览器 localStorage 保存演示数据；其浏览器检查证据为 prototype_only。

已确认的架构约束：
- Desktop / Web 共用领域模型和核心业务规则。
- 本地优先；云同步不作为当前首版前置条件。
- UI 不直接访问数据库或操作系统文件 API。
- 业务状态变更通过 Application Use Case 执行。
- Plan（预定安排）与 WorkSession（实际执行）分开保存。
- Deadline、Goal / Stage 日期与 Plan 日期语义分离。
- 外部引用不自动上传；文件夹引用默认不递归扫描。
- 原型交互验收不等于正式应用开发完成。

## 2. 推荐技术方案（待确认）

### 2.1 技术组合

| 层次 | 推荐选择 | 说明 |
|---|---|---|
| UI | React + TypeScript | Desktop / Web 共用组件与交互 |
| 开发构建 | Vite | 前端开发、构建与本地预览 |
| 桌面容器 | Tauri 2 | Windows 首发桌面容器；后续可扩展其他桌面平台 |
| 桌面持久化 | SQLite | 本地正式业务数据库 |
| Web 持久化 | IndexedDB | 浏览器本地存储适配，不假设浏览器可直接访问本地 SQLite 文件 |
| 领域与用例 | 纯 TypeScript 模块 | 不依赖 React、Tauri 或具体数据库 |
| 数据访问 | Repository 接口 + 平台实现 | UI 与业务用例不直接拼 SQL |
| 桌面桥接 | Tauri Commands / Plugin Adapter | 仅暴露明确、受控的应用能力 |
| 测试 | Vitest + Playwright | 领域单测、存储集成测、关键流程 E2E |

建议以 Desktop 本地优先为首发落地目标，同时保留 Web 构建与 IndexedDB Adapter。若决定首发必须同时支持 Web 与 Desktop，应把两端持久化适配器列入首个发布验收，而不是只做静态 Web 外壳。

### 2.2 代码分层

```text
apps/
  desktop/              # Tauri 容器与桌面入口
  web/                  # Web 入口
packages/
  ui/                   # 共用 React 组件
  domain/               # 实体、值对象、领域规则
  application/          # 用例、命令、查询、校验
  contracts/            # DTO、Repository 接口、平台能力接口
  infrastructure/
    sqlite/             # SQLite Repository 与 Migration
    indexeddb/          # Web IndexedDB Repository
    platform/           # 文件、通知、打开 URL 等 Adapter
  test-utils/           # 测试工厂与共享测试数据
docs/
  ...
```

这是建议目录，不要求为了套用结构而重写现有文档或原型。正式初始化时应先建立最小可运行骨架，再按实际依赖落位。

## 3. 核心数据契约（逻辑级，非最终 DDL）

### 3.1 Task

关键字段建议：
- `id`、`parent_task_id`
- `title`、`description`
- `priority`、`estimate_minutes`
- `deadline`（独立于 Plan）
- `lifecycle_status`
- `goal_id`、`stage_id`（规划关联；允许为空）
- `created_at`、`updated_at`、`archived_at`、`deleted_at`

调度状态应优先由有效 Plan 推导，避免同时写入 Task 与 Plan 后出现状态不一致。若后续为查询性能保存冗余状态，必须通过事务维护并提供一致性校验。

### 3.2 Plan

关键字段建议：
- `id`
- `task_id`（首个纵向闭环必填）
- `plan_date`
- `start_at`、`end_at`（可空；若采用时间块，开始和结束必须成对填写且开始早于结束）
- `timezone`
- `status`（planned / cancelled）
- `previous_plan_id`（可选的接续关系）
- `created_at`、`updated_at`

约束：
1. 一个 Task 可以有多个 Plan。
2. 移动或调整 Plan 更新同一 Plan ID，不复制 Task。
3. 取消 Plan 不删除 Task，也不删除历史 WorkSession。
4. Deadline 不从 Plan 推导；Plan 变更不修改 Deadline。
5. 首个纵向闭环先实现 Task Plan；HabitOccurrence 的 Plan 在 Habit 阶段扩展。
6. 所有时间点保存明确时区语义；日期型字段使用日期语义，不伪装成 UTC 时间点。

### 3.3 WorkSession

关键字段建议：
- `id`、`task_id`
- `started_at`、`ended_at`
- `actual_seconds`
- `created_at`

约束：
- WorkSession 记录实际投入，不由 Plan 时长计算。
- 一个 Task 可以有多条 WorkSession。
- 结束或补录执行记录不得修改 Plan 的原定时间。
- 计时以时间戳为事实来源；页面刷新或应用重启后应能恢复未结束会话状态。

### 3.4 Goal / Stage 关联

Goal / Stage 保持独立实体。Task 可直接关联 Goal，也可关联 Goal 下的 Stage；不强制每个 Task 都属于规划对象。修改 Goal / Stage 日期不自动级联修改 Task Plan。

## 4. 首个正式纵向闭环

建议把 v1.0 的首个可验收切片定义为：

1. 应用启动并初始化本地数据库。
2. 创建、编辑、完成、归档 Task。
3. 未安排 Task 出现在未安排任务池。
4. 创建 Plan，并在日视图 / 甘特图中读取同一条数据。
5. 拖动或编辑时间条，更新同一个 Plan。
6. Deadline 独立显示和编辑。
7. 检查时间冲突并向用户明确提示，不静默覆盖其他 Plan。
8. 用户确认后可保留冲突安排；不自动重排其他任务。
9. 从 Task 开始和结束 WorkSession，持久化实际投入。
10. 重启应用后，Task、Plan、WorkSession 均可恢复。
11. 使用同一 Task ID 在列表、甘特图和调度首页之间切换，不生成重复对象。

Goal / Stage 的完整 CRUD、Candidate、Habit、CalendarEvent、Review 等按既有 Roadmap 分阶段接入，不把它们全部塞进首个切片。

## 5. 数据迁移与备份

- 正式数据库使用有序、可重复验证的 schema migration。
- 每次升级前创建可恢复备份；迁移失败不得覆盖唯一原始数据。
- v0.8 / v0.9 localStorage 是浏览器原型数据，不自动视为正式数据库。
- 提供 JSON 导出与导入预览：展示对象数量、字段映射、冲突和无效记录。
- 用户确认导入后再写入正式库；保留导入前快照。
- 导入不得静默覆盖已有 Task、Plan 或 Goal。
- 本地绝对路径作为外部引用保留元数据；失效时允许重新定位。

## 6. 一致性、冲突与错误处理

- Task、Plan、WorkSession 的关键写入通过事务或等效原子操作完成。
- Plan 时间冲突默认提示，不自动移动或覆盖其他 Plan。
- 更新 Plan 使用稳定 ID；拖动失败时恢复 UI 到数据库已确认状态。
- 取消、归档、删除分开处理；删除优先软删除并保留恢复信息。
- UI 显示保存中、保存成功、保存失败和重试状态；不得先显示成功再异步吞掉错误。
- 所有业务时间按用户时区显示，存储时保留明确时间语义。

## 7. 测试与验收策略

| 层次 | 测试重点 |
|---|---|
| Domain 单测 | Task 生命周期、Plan 日期校验、Deadline 与 Plan 分离 |
| Application 测试 | 创建 Task、创建 / 移动 / 取消 Plan、开始 / 结束 WorkSession |
| Repository 集成测试 | SQLite / IndexedDB 持久化、事务、迁移、恢复 |
| E2E | 创建 Task → 排期 → 拖动 → 执行 → 完成 → 重启恢复 |
| 兼容测试 | 导入旧版 JSON、缺字段迁移、重复导入保护 |
| UI 测试 | 1440px 桌面、768px 平板、390px 窄屏、键盘操作 |

只有真实应用在目标环境通过上述关键验收，才能将状态从 prototype_only 提升为 verified；静态检查和单文件 HTML 演示不能替代。

## 9. 本次需要确认的产品 / 技术决策

### DEC-PROPOSED-01：首发平台范围
- 推荐：Windows Desktop 优先，Web 保持同一领域与应用层，Web 持久化 Adapter 随首发范围决定。
- 备选：Desktop 与 Web 同时作为首发交付，需同时完成两端持久化与验收。

### DEC-PROPOSED-02：本地数据策略
- 推荐：Desktop 使用 SQLite；Web 使用 IndexedDB；首版不做云同步。
- 需要确认：是否接受 Web 与 Desktop 各自本地保存、通过导入 / 导出交换数据，而非实时双向同步。

### DEC-PROPOSED-03：冲突策略
- 推荐：冲突只提示，不自动重排；用户明确确认后允许保存重叠 Plan。
- 若希望禁止重叠，需要另行定义冲突范围（同一 Task、不同 Task、日历事件、习惯实例）。

## 10. 本提案不代表已冻结或已实现

本文件是供评审的技术方案建议。用户确认首发平台、Web 数据策略和冲突策略后，才更新正式架构、ADR、数据模型和开发任务状态。当前不创建生产数据库、不把原型 localStorage 升级为正式存储，也不将未实现能力标记为完成。
